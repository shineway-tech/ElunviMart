# ElunviMart 用户、子账号与会员体系设计

## 设计状态

这是前端 Electron 客户端和后端 API 的业务设计基线，当前只定义边界、数据关系和权益规则，不包含实现代码。

已确认的业务规则：

- 用户使用邮箱和密码登录，不使用手机号。
- 注册后必须验证邮箱，验证前不能正常使用工作区功能。
- 会员归属于商家工作区/主账号，子账号共享工作区会员。
- 一个邮箱对应一个平台用户，一个用户可以加入多个工作区。
- 前端和后端是两个独立 Git 仓库。

## 系统边界

前端仓库负责桌面端界面、本地拼多多登录会话、本地商品缓存、同步任务和本地通知配置。后端仓库负责平台身份、工作区、成员权限、会员订阅、权益计算、用量统计和审计记录。

拼多多 Cookie、Anti-Content、商家登录凭证和营销列表请求仍然只在前端本地处理，不上传到后端。后端只接收当前平台用户身份、工作区上下文和必要的业务统计数据。

## 核心概念

### 用户 User

用户是平台登录主体，邮箱是唯一标识。用户需要具备以下状态：

- `pending_email_verification`：已注册但未完成邮箱验证；
- `active`：可正常登录和使用工作区；
- `disabled`：被平台或工作区安全策略禁用。

用户可以加入多个工作区，但同一邮箱在同一工作区只能有一个成员关系。

### 工作区 Workspace

工作区代表一个商家或团队，是权限、会员和用量的隔离边界。工作区拥有：

- 一个或多个拼多多店铺账号；
- 一个会员订阅；
- 一组成员和角色；
- 商品监控用量、同步用量和通知配置；
- 操作审计记录。

首次注册用户会创建一个工作区，并成为该工作区的主账号。

### 工作区成员 Workspace Member

成员关系连接用户和工作区。成员状态包括邀请中、已加入、已移除和已禁用。邀请通过邮箱发送，邀请链接具有有效期和一次性使用限制。

如果被邀请邮箱已经注册，用户登录后接受邀请即可加入；如果邮箱尚未注册，先完成注册和邮箱验证，再接受邀请。

### 拼多多店铺账号 Merchant Account

店铺账号归属于工作区，不归属于某个子账号。成员通过角色权限操作店铺，但拼多多登录会话仍保留在使用该店铺的本地客户端中。

### 会员订阅 Subscription

订阅归属于工作区。主账号负责购买、续费、取消和查看订阅信息，子账号不能单独购买或改变工作区会员。

订阅状态采用以下状态流转：

```text
trialing → active → past_due → grace_period → expired
                    ↘ canceled
```

订阅状态由后端维护，客户端只能读取结果，不能自行延长会员有效期。

## 登录与安全流程

### 注册和验证

注册时提交邮箱和密码。邮箱统一转小写并去除首尾空格后作为唯一键。系统创建待验证用户并发送一次性验证邮件，验证链接使用随机 Token，后端只保存 Token 哈希和过期时间。

邮箱未验证时可以重新发送验证邮件，但需要限流；验证成功后用户状态变为 `active`。未验证用户不能创建工作区、接受成员邀请、绑定店铺或执行同步。

### 登录和会话

登录使用邮箱和密码。访问令牌短期有效，刷新令牌按设备单独管理并支持撤销。退出登录时撤销当前设备的刷新令牌，用户可以在安全设置中撤销其他设备。

密码只保存强哈希值，不保存明文。密码重置通过一次性邮箱 Token 完成，重置后撤销该用户的其他刷新会话。

### 高风险操作

修改邮箱、修改密码、移除主账号、转移工作区所有权和取消订阅需要重新验证当前密码。修改邮箱需要同时验证新邮箱，旧邮箱收到安全通知。

## 角色与权限

会员决定工作区能用多少和能不能使用某项产品能力，角色决定成员能执行什么操作。两者必须同时满足才能放行。

初始角色如下：

| 角色 | 能力 |
| --- | --- |
| 主账号 | 管理会员、成员、店铺、通知、工作区和全部数据 |
| 管理员 | 管理成员、店铺和监控配置，不能操作会员支付和所有权转移 |
| 运营人员 | 执行同步、查看商品、处理监控和通知 |
| 查看人员 | 只读查看商品、状态和同步结果 |

权限采用稳定的权限编码，避免把会员名称写进授权逻辑：

- `member.view`、`member.manage`；
- `merchant.view`、`merchant.manage`；
- `product.view`、`product.sync`；
- `notification.view`、`notification.manage`；
- `billing.view`、`billing.manage`；
- `audit.view`；
- `data.export`。

## 三档会员权益

会员档位只是一组权益配置。后端保存权益键和值，客户端显示权益但不作为最终判断依据。

| 权益 | 基础版 | 专业版 | 企业版 |
| --- | ---: | ---: | ---: |
| 工作区数量 | 1 | 3 | 10 |
| 子账号数量 | 2 | 10 | 50 |
| 拼多多店铺数量 | 1 | 5 | 10 |
| 最短自动同步间隔 | 30 分钟 | 10 分钟 | 5 分钟 |
| 桌面通知 | 支持 | 支持 | 支持 |
| 企业微信/钉钉通知 | 1 个 | 多个 | 多组配置 |
| 数据导出 | 不支持 | 支持 | 支持 |
| 操作审计 | 不支持 | 基础审计 | 完整审计 |
| 技术支持 | 标准 | 优先 | 专属 |

拼多多店铺数量是产品级硬上限，任何会员档位最多只能绑定 10 个店铺。会员权益只能限制各档位的实际可用数量，不能突破这个上限。

推荐权益键包括：

- `max_workspaces`；
- `max_members`；
- `max_merchants`；
- `min_sync_interval_minutes`；
- `notification_channels`；
- `can_export`；
- `can_audit`。

当会员降级时，已存在的数据不立即删除；新建成员、店铺和同步任务按新额度阻止，并提示用户处理超额数据。会员恢复或升级后立即解除对应限制。

## 数据模型边界

后端需要围绕以下实体设计：

- `users`：邮箱、密码哈希、验证状态和安全状态；
- `email_verifications`：验证邮件 Token 哈希、用途和过期时间；
- `password_resets`：密码重置 Token 哈希和使用状态；
- `workspaces`：商家工作区基本资料和所有权信息；
- `workspace_members`：用户、工作区、角色和成员状态；
- `workspace_invitations`：邀请邮箱、角色、过期时间和使用状态；
- `roles`、`permissions`、`role_permissions`：角色授权；
- `plans`、`plan_entitlements`：会员档位和权益配置；
- `subscriptions`：工作区当前订阅、周期、状态和宽限期；
- `subscription_events`：支付或后台变更事件，保证订阅状态可追溯；
- `usage_counters`：成员、店铺、商品和导出等用量；
- `device_sessions`：刷新令牌哈希、设备信息、过期时间和撤销状态；
- `audit_logs`：成员、权限、订阅和敏感操作记录。

## 前后端交互

后端提供四组能力：

1. **身份**：注册、邮箱验证、登录、刷新会话、退出、密码重置；
2. **工作区**：当前工作区、成员邀请、角色变更、店铺元数据；
3. **会员**：当前订阅、会员档位、权益快照、用量和订阅事件；
4. **审计**：管理员查看工作区内的关键操作记录。

前端启动后拉取当前用户、工作区成员关系和权益快照，并在本地缓存短期快照。执行同步前由后端返回的权益快照做快速判断，关键操作仍由后端再次校验。网络不可用时可以继续查看本地缓存，但涉及会员限制的新增操作需要在线确认，避免长期离线绕过权益限制。

## 现有数据迁移

现有前端本地 `accounts` 表中的商家账号迁移为工作区下的店铺账号。迁移时：

1. 第一个现有商家账号创建初始工作区；
2. 当前使用者绑定为主账号；
3. 现有商品缓存继续保存在本地，不强制上传；
4. 店铺名称、店铺 ID、同步状态迁移为店铺元数据；
5. 拼多多登录会话不迁移到后端；
6. 如果无法确认当前使用者邮箱，先要求完成平台账号注册和邮箱验证，再执行绑定。

## 本地和线上环境

本地开发环境和线上环境使用完全独立的配置、数据库、缓存、邮件服务和密钥。任何环境都不能通过默认值连接另一套环境。

| 项目 | 本地开发环境 | 线上环境 |
| --- | --- | --- |
| API 地址 | `http://localhost` 开发地址 | 独立 HTTPS 域名 |
| 数据库 | 本地 Docker MySQL，独立数据库名 | 独立生产 MySQL 实例 |
| Redis | 本地 Docker Redis | 独立生产 Redis 实例 |
| 邮件 | Mailpit 或本地邮件捕获服务 | 正式邮件服务和发件域名 |
| 密钥 | `.env.local`，只存在开发机 | 部署平台 Secret/密钥管理服务 |
| 前端配置 | 开发 API 地址 | 构建时注入线上 API 地址 |
| 数据 | 测试账号和测试会员 | 真实用户和订阅数据 |

线上邮件服务使用腾讯企业邮 SMTP，非敏感连接参数如下：

- Host：`smtp.exmail.qq.com`；
- Port：`465`；
- Secure：`true`；
- Username：`support@honeykid.cn`；
- From email：`support@honeykid.cn`；
- From name：`support`。

SMTP 密码只通过线上 Secret 注入，不写入仓库、`.env.example`、日志或设计文档。开发环境继续使用 Mailpit，不连接线上邮箱。

后端配置按环境拆分为公共配置、开发配置和生产配置。仓库只提交 `.env.example`，不提交真实密钥、数据库密码、JWT 签名密钥、邮件凭证或支付凭证。生产环境必须显式设置环境标识，缺少关键配置时服务拒绝启动。

前端只保存 API 地址和非敏感环境标识，不把后端密钥打包进 Electron。登录令牌继续使用系统安全存储；本地开发和线上环境使用不同的令牌签名密钥，开发令牌不能访问生产 API。

## 数据库迁移和初始化

后端数据库采用版本化 migration，不允许通过启动时自动建表代替迁移。每次 schema 变化新增一个有序迁移文件，并在数据库中记录已执行版本。

迁移规则如下：

1. 本地启动前执行迁移，未执行的迁移按顺序补齐；
2. 线上发布由独立 release 步骤执行迁移，应用进程不自行竞争迁移锁；
3. 破坏性变更采用扩展、回填、切换、清理四步，不能直接删除线上仍在使用的字段；
4. 生产迁移前执行数据库备份和结构检查；
5. 迁移失败时停止发布，不启动使用新结构的应用版本；
6. 角色和三档会员权益使用幂等 seed 初始化，重复执行不会重复插入；
7. 本地测试数据库可以重建，线上数据库只能通过迁移修改。

第一批迁移覆盖用户、邮箱验证、密码重置、工作区、成员、邀请、角色、权限、会员档位、权益、订阅、设备会话、用量和审计表。现有前端 SQLite 数据迁移属于一次性数据导入任务，不和后端 schema migration 混在一起。

## 发布和回滚

本地使用 Docker Compose 启动 MySQL、Redis、Mailpit 和后端 API，提供一套可重复的初始化命令。线上部署顺序固定为：构建镜像、备份数据库、执行兼容迁移、启动新版本、健康检查、切换流量。

应用需要提供健康检查和就绪检查。健康检查只验证进程可用，就绪检查还要验证数据库连接、Redis 连接和邮件服务配置。迁移或启动失败不能自动切换到另一套环境。

回滚优先回滚应用版本；数据库只允许执行已经验证过的向前兼容迁移，不能依赖未经验证的自动 down migration 恢复生产数据。

## 分阶段建设顺序

第一阶段建设本地/线上配置、Docker Compose、数据库迁移基线、幂等 seed 和健康检查。

第二阶段建设邮箱用户、邮箱验证、登录会话和工作区主账号。

第三阶段建设子账号邀请、角色权限和工作区成员管理。

第四阶段建设三档会员、权益配置、用量统计和前端限制提示。

第五阶段接入支付或后台开通订阅、订阅状态同步、宽限期和审计报表。

第六阶段迁移现有本地商家账号，并支持多设备登录和跨设备工作区数据。

## 第一版明确不做的内容

- 手机号注册、短信验证码和手机号找回；
- 社交登录和企业 SSO；
- 子账号独立购买会员；
- 将拼多多 Cookie 或 Anti-Content 上传后端；
- 复杂的自定义角色编辑器；
- 会员降级时自动删除超额数据。

## 待业务确认的参数

以下内容不影响整体架构，但在实现订阅和支付前需要确定：

- 三档会员的正式名称和价格；
- 是否提供注册试用期，以及试用期天数；
- 企业版是否需要人工审核开通；
- 支付渠道和退款规则；
- 线上部署平台、数据库和 Redis 服务商；
- 线上 API 域名和邮件发件域名；
