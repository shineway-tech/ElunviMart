# 营销竞价商品列表响应捕获设计

## 目标

将营销竞价商品同步改为“页面请求、应用读取响应”的模式。隐藏 Electron 页面负责登录态、Cookie、请求头和 `Anti-Content`，应用只捕获并解析页面自身发出的 `bidList` 响应，不再从 Node 侧手工拼接带 `Anti-Content` 的重复请求。

成功标准：

- 商品同步使用隐藏营销竞价页面的真实网络请求。
- Node 侧不再调用 `executeJavaScript(fetch('/lakemms/bid/query/bidList'))`。
- 同一账号同一时间最多一个页面同步任务。
- 页面加载、响应捕获、分页和失败重试都有明确超时和退避行为。
- 现有商品归并、掉标判断、通知和本地缓存行为保持不变。

## 页面会话与生命周期

每个账号维护一个独立的隐藏监控窗口和持久化 partition。完成登录后，窗口导航到营销竞价页面；窗口保持隐藏，作为后续同步的真实浏览器上下文。用户可见的登录窗口不应被同步流程强制导航到营销页面。

在页面导航前接入 Electron `webContents.debugger` 的 `Network` 域，监听 `responseReceived`。只处理拼多多 `bidList` 路径的响应，并按账号保存待解析的响应任务。页面关闭、调试器断开或账号移除时清理监听器、响应缓存和窗口引用。

## 响应捕获

响应事件到达后，检查 URL、HTTP 状态和请求方法，再通过 `Network.getResponseBody` 读取响应体。响应体解析为 JSON 后交给现有 `mapBidListResponse`，复用现有字段映射和错误码处理。

捕获结果应包含：

- 请求页码
- 页面大小
- 接口返回的 `total`
- 当前页商品
- 接口错误码
- 请求时间和响应时间

捕获器只负责网络响应和超时，不负责商品归并或通知。

## 分页

首次同步通过营销页面自然加载得到第一页响应，并从对应请求体记录分页参数。若 `total` 大于第一页商品数，后续页在页面上下文中调用页面已有的 `fetch`，使用相同的 URL、Cookie 和页面请求头，由页面环境自行附带有效的 `Anti-Content`。每页请求之间加入随机延迟，并通过响应捕获器接收结果。

应用不再直接调用 Node 侧 `fetch` 或手工设置 `Anti-Content`。分页最多执行配置的页数和商品数预算；达到预算时同步失败并保留旧缓存，避免异常接口响应造成无界请求。

## 同步状态机

每个账号使用串行队列：

1. 检查窗口存在且未销毁。
2. 检查页面仍处于营销竞价页，否则在隐藏窗口中导航。
3. 等待页面响应捕获器得到第一页。
4. 按 `total` 在页面上下文中请求剩余分页。
5. 等待所有页响应并合并商品。
6. 调用现有 `reconcileProducts`、持久化和通知逻辑。

自动同步和手动同步共用同一队列。队列运行期间的新请求不并发执行；手动请求可以返回“同步进行中”，自动任务则跳过本轮。

## 错误处理

- 页面加载失败：结束本次同步，保留缓存并记录错误。
- 登录页或 HTTP 401/403：将账号标记为 `needs_login`。
- `54001`：不在当前同步内立即刷新重试；记录失败次数，使用指数退避安排下一次同步。
- 响应体不可读或格式错误：本次同步失败，不覆盖旧商品缓存。
- 页面响应超时：取消本次等待，清理该账号的待处理响应。

页面刷新只允许由会话恢复逻辑触发，不允许每次同步无条件刷新。

## 模块边界

- `src/main/merchant-session.js`（新增）：账号窗口、隐藏页面和 debugger 生命周期。
- `src/main/pdd-response-capture.js`（新增）：Network 事件、响应体读取、超时和按请求匹配。
- `src/main/pdd-adapter.js`：改为调用页面同步器，保留响应校验和商品映射。
- `src/main/main.js`：注入会话管理器和同步队列，保留归并、通知和 IPC 接口。
- `src/main/scheduler.js`：只负责调度，不直接处理请求并发。

## 验证

- 单元测试覆盖响应 URL 过滤、响应体解析、分页合并、超时、`54001` 退避和账号级串行锁。
- 集成测试使用模拟 `webContents.debugger` 事件验证：页面响应可以完整转换为商品列表，Node 侧没有直接 `bidList` fetch。
- 手动验证登录、自动同步、手动同步、分页、登录失效和窗口关闭后的恢复路径。
